Design and implementation review — 23 October 2026
================================================

> Historical snapshot from earlier on 23 October. The transaction adapter,
> Oracle workflow submission constraint, typing/CI, workflow test coverage, and
> main minimum-dependency pins discussed below have since changed. Current
> findings, verification, and remaining tasks are in the
> [consolidated backlog](../todo-task.md). Do not use this review as an active
> task list.

The PostgreSQL task engine is substantially implemented and passes its local
correctness and operator checks. The project does not yet meet the design's
release acceptance contract. The largest current implementation defect is that
the advertised database adapters are bypassed by the coordination transaction
used throughout the task engine. The newer workflow feature also needs its own
acceptance suite and an Oracle schema correction.

This review compares the current working tree with
[`Django tasks design.md`](../Django%20tasks%20design.md), the
[implementation specification](implementation-spec.md), and the
[acceptance status](acceptance-status.md). The 19 October
[review](project-review.md) is historical; its findings should not be treated as
new defects without checking the subsequent fixes. Most implementation files
are currently untracked, and HEAD is the initial commit, so these observations
describe the working tree rather than a released or reproducible source tag.
Runtime code was not changed. No AWS resources were deployed.

**Findings, ordered by impact**

1. **P1 — Non-PostgreSQL coordination fails despite the advertised support.**

   [services/lifecycle.py:18](../src/django_tasks_aws/services/lifecycle.py#L18)
   still implements `coordination_transaction()` with PostgreSQL
   `current_setting`, `SET LOCAL`, and `set_config` statements. It never calls
   the selected database adapter's `transaction()` implementation. Claims,
   dispatch reservations, finalization, reconciliation, invariant inspection,
   and retention all use this helper. Enqueue can therefore accept durable work
   on another engine while publication and execution cannot progress through
   the normal protocol.

   The adapter transaction methods exist, but are not wired into this shared
   boundary. Executing the helper's opening SQL against disposable MariaDB
   10.11 produced `ERROR 1305: FUNCTION ...current_setting does not exist`.
   MySQL and Oracle failure follows from the same unconditional PostgreSQL SQL;
   their complete lifecycle paths were not executed in this review. The host's
   MySQL client also lacks MariaDB's authentication plugin, so the MariaDB SQL
   reproduction used the container's bundled client.

   **Improve:** Delegate this helper to
   `database_adapter(alias).transaction(connections[alias])`, then verify
   session-limit restoration, rollback, nested transactions, claims, stale
   finalization, dispatch, and recovery against each claimed engine. This is a
   functional blocker for the README's four-engine support claim and the
   database-portability update to the design.

2. **P2 — Oracle workflow submissions repeat the nullable-key problem already
   fixed for ordinary tasks.**

   [workflows/models.py:43](../src/django_tasks_aws/workflows/models.py#L43)
   and its initial migration use an ordinary unique constraint on
   `(backend_alias, submission_key)`, while `submission_key` is optional.
   Oracle treats repeated composite keys with the same non-NULL backend and a
   NULL submission key as duplicates. Consequently, a second unkeyed workflow
   for a backend will fail. `_accept_run()` re-raises the integrity error for
   an absent key.

   This is a schema finding, not a live Oracle reproduction. The repository
   already documents and handles exactly this engine behavior for ordinary
   tasks with `SubmissionKeyConstraint` and migration 0009.

   **Improve:** Apply the same NULL semantics to workflow submission identity
   through a migration. Test multiple unkeyed workflows, keyed deduplication,
   and changed-definition conflicts on Oracle.

3. **P2 — The automated support matrix omits the new capabilities.**

   [tests/settings.py:16](../tests/settings.py#L16) does not install the
   workflow app. There are no workflow regression tests or dedicated
   MySQL/MariaDB/Oracle lifecycle suites in the current tests. Both regular CI
   and the release candidate matrix exercise PostgreSQL; the candidate matrix
   varies Python, PostgreSQL version, and dependency-bound labels. The 94-row
   verification inventory does not cover the new workflow contract or expand
   its invariants across the new database engines.

   A manually enabled two-step PostgreSQL workflow completed successfully in
   this review. That establishes a basic working path, not the documented
   concurrency, recovery, or retention behavior. Existing passing tests cannot
   detect findings 1 and 2.

   **Improve:** Add database contract suites using independent connections, and
   an opt-in workflow suite covering transactional rollback, duplicate
   submissions, competing advancement, fan-out/fan-in, output selection,
   preparation failure, held parents, failed descendants, lost callbacks,
   sweeper recovery, result-retention protection, and installed migrations.
   Include these in candidate evidence, or narrow the support statement until
   their evidence exists.

4. **P2 — The documented type check fails, and CI does not run it.**

   `mypy` reports **19 errors in five workflow files**: untyped parent maps,
   model-manager attributes absent from the configured Django-stubs app
   registry, backend attributes inferred as `BaseTaskBackend`, and a union
   index used against a list. `make check` includes mypy, so the documented
   contributor check is currently broken. The
   [CI lint job](../.github/workflows/ci.yml#L26) runs Ruff and traceability but
   omits mypy, allowing this discrepancy to survive.

   **Improve:** Correct the workflow typing and type-check app configuration,
   then make CI execute the same check advertised to contributors. Do not
   suppress the entire optional app to obtain a passing result.

5. **P2 — The “minimum” dependency lane provides only partial lower-bound
   coverage.**

   [scripts/verify_installed.py:80](../scripts/verify_installed.py#L80)
   pins only Django and boto3 in minimum mode. Powertools, Pydantic, Tenacity,
   and the PostgreSQL driver can resolve to newer versions despite their
   declared lower bounds. Optional database-driver combinations are absent as
   well. This does not prove a current incompatibility; it limits the evidence
   supplied by a successful minimum-labelled receipt.

   **Improve:** Define and record a reproducible compatible lower-bound set for
   the supported runtime dependencies and engine extras, or explicitly describe
   the lane as testing Django/boto3 lower bounds. Keep resolved versions in the
   candidate evidence.

The design explicitly excludes workflow graphs from its original release
baseline, while the README now advertises them as an optional extension. That
extension should have separate requirement IDs and support boundaries. The
older acceptance status also predates the workflow and database expansion.
Update those contracts to describe the current product and its evidence.

Priority scheduling, coroutine execution, strict rate limiting, FIFO ordering,
heartbeat-based long-running tasks, cancellation, and compensation are not
missing first-release deliverables under the current design. Adding them would
expand scope before the existing acceptance work is complete.

The strict traceability failure is expected for these local reports: the
missing assignments require AWS or clean-installed-artifact results. It does
not mean those tests were executed and failed. The release gate correctly
refuses to treat local test success as complete acceptance. Capacity/cost and
the full support matrix have additional candidate requirements beyond this
traceability check.

prefix `django-tasks-review-` and date `20261023`. Distribution artifacts are in
`/private/tmp/django-tasks-review-dist-20261023/`. Review databases were isolated
in two disposable containers; both containers were removed. Existing databases
were not used.

**Recommended next work**

1. Repair the transaction adapter boundary and Oracle workflow constraint.
   Add targeted regressions that fail on the current code.
2. Add the engine and workflow acceptance suites, resolve the type errors, and
   make CI run the documented developer checks.
3. Align the frozen contract, support statements, verification inventory, and
   acceptance status with the expanded feature set and actual test evidence.
4. Verify an identified wheel/source candidate through clean installation and
   the complete compatibility matrix, then run disposable AWS fault,
   operations, rollout/rollback, and cleanup scenarios.
5. Execute the specified capacity/cost experiments and full release rehearsal
   before describing the package as production-ready or publishing it.
